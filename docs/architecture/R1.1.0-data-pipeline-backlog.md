## 1. Overview & Objectives

This backlog defines technical improvements for the **FPL DOF Ingestion and Data Platform**. The initiatives focus on enhancing point-in-time fidelity (strict temporal scoping without lookahead leakage), creating unified multi-season views in Gold, eliminating redundant historical network ingress, and standardizing match odds across past and current seasons.

### PIPE-01: Season + Gameweek Temporal Scoping & Retrospective Ingress

- **Theme**: Temporal Integrity & Walk-Forward Fidelity (Reference: `data-pipeline-design.md` §1.4 & §4).
- **Priority**: High

#### Background & Problem Statement
Currently, Invariant 5 dictates that scraped aggregate sources (such as Understat and FBref) are conformed with `scope="season"` and `gameweek=None` to prevent full-season totals from masquerading as single gameweek observations. However, this creates a coarse grain: backtest models running at GW1 can either see the entire season's totals (lookahead bug) or none of it (information loss). Furthermore, when a new source is added mid-season (e.g. at GW10), there is no standardized protocol to reconstruct what was known prior to each earlier gameweek.

#### Proposed Design & Solution
1. **Granular Temporal Stamping**:
   - Refactor `Table.PLAYER_ADVANCED` and `Table.PLAYER_METRIC` to index by `season` AND `as_of_gameweek`.
   - In season `2026/27` at `GW1`, models only access information published prior to the GW1 deadline.
   - At `GW5`, models access observations prior to the GW5 deadline, containing the complete progressive history of GW1, GW2, GW3, GW4, GW5, plus all prior seasons.
2. **Backdated Retrospective Ingress for New Sources**:
   - When a new source is introduced mid-season (e.g. at GW10):
     - If the source provides timestamped match logs, map entries to the corresponding FPL gameweek deadlines:
       $$\text{GW}_k \iff T_{\text{event}} < T_{\text{deadline}}(\text{GW}_k)$$
     - If the source only exposes running totals without match logs, generate backdated best-effort snapshot estimations for GW1 through GW9 based on available historical timestamps.
     - Record the match method and provenance in `Table.PLAYER_CROSSWALK` and metadata.

- [`pipeline/src/fpl_dof/silver/tables.py`](file:///c:/JHH/source/fpl_dof2/pipeline/src/fpl_dof/silver/tables.py) (`METRIC_SCOPES`, `PlayerAdvancedSchema`, `PlayerMetricSchema`)
- [`pipeline/src/fpl_dof/sources/understat/adapter.py`](file:///c:/JHH/source/fpl_dof2/pipeline/src/fpl_dof/sources/understat/adapter.py)
- [`pipeline/src/fpl_dof/sources/fbref/adapter.py`](file:///c:/JHH/source/fpl_dof2/pipeline/src/fpl_dof/sources/fbref/adapter.py)

#### Acceptance Criteria
- [ ] No metric stamped with `as_of_gameweek = N` contains data whose event or observation timestamp was after the GW $N$ deadline.
- [ ] Walk-forward simulation at GW $N$ yields identical feature vectors whether executed during GW $N$ or replayed at GW $N+10$.
- [ ] Newly ingested sources backfill incremental snapshots for historical gameweeks with verified non-leakage tests.

### PIPE-02: Unified Multi-Season Player View in Gold (Archive + Cache + API)

- **Theme**: Data Unification & Long-Horizon Modeling (Reference: `data-pipeline-design.md` §3.1, §3.4 & §4).
- **Priority**: Medium-High

#### Background & Problem Statement
Currently, multi-season player history is fragmented across three separate components:
1. `fpl` adapter provides current season stats and aggregated `history_past` season summaries.
2. `fplarchive` provides granular past-season gameweek CSVs (Vaastav mirror).
3. `fplcache` holds pinned frozen deadline snapshots up to GW38 2025/26.
Downstream models and prospective harnesses must reconcile these sources ad-hoc. Furthermore, FPL re-indexes integer `player_id` (`element`) every season, creating severe risk of cross-season identity corruption if keys are conflated.

#### Proposed Design & Solution
1. **Unified Gold Player Dataset (`player_career_history`)**:
   - Establish a conformed Gold dataset combining historical gameweek actuals from `fplarchive`, frozen snapshots from `fplcache`, and live `element_summary` from the `fpl` API.
2. **Career-Stable Key Enforcement**:
   - Strictly join and index cross-season records using FPL's permanent `player_code` (`code`), never seasonal `player_id`.
   - Maintain a canonical crosswalk mapping `(season, player_id) -> player_code`.
3. **Harmonized Defensive & Metric Columns**:
   - Explicitly store Defensive Contribution components prior to 2025/26 as `null` (not zero) to uphold DL-18.
   - Standardize club identifiers across seasons using permanent team codes.

#### Affected Components

- [`pipeline/src/fpl_dof/sources/fplarchive/adapter.py`](file:///c:/JHH/source/fpl_dof2/pipeline/src/fpl_dof/sources/fplarchive/adapter.py)

#### Acceptance Criteria
- [ ] A single Gold artifact or query interface yields a player's complete gameweek history across all available historical and current seasons.
- [ ] Reassigned seasonal player IDs never collide across seasons.
- [ ] Defensive metrics prior to 2025/26 remain strictly nullable.

### PIPE-03: Zero-Re-fetch Immutable Acquisition for Prior Seasons

- **Theme**: Cost Discipline & Pipeline Ingress Optimization (Reference: `data-pipeline-design.md` §3.4 & §5).
- **Priority**: Medium

#### Background & Problem Statement
Historical data from completed seasons (such as past FPL archive data) is immutable by definition. While `fplarchive` currently specifies a 1-year cache TTL (`_YEAR`), network checks or full re-runs can still trigger redundant file requests or depend on external GitHub mirrors during local or CI runs.

#### Proposed Design & Solution
1. **Permanent Frozen Bronze Tiers**:
   - Mark finished historical seasons as permanently frozen (`immutable=True` on `Resource` or `IngestRequest`).
   - Store historical archive data in a committed or persistent storage partition (`data/bronze/archive/`) that bypasses TTL expiration.
2. **Explicit Re-acquisition Guard**:
   - Ingestion bypasses network checks entirely for frozen seasons unless an explicit `--rebackfill` or `--fix-defect` flag is supplied.
   - Eliminates external mirror availability risks during ordinary weekly pipeline runs.

#### Affected Components
- [`pipeline/src/fpl_dof/sources/base.py`](file:///c:/JHH/source/fpl_dof2/pipeline/src/fpl_dof/sources/base.py) (`Resource`, `IngestRequest`)
- [`pipeline/src/fpl_dof/sources/fetch.py`](file:///c:/JHH/source/fpl_dof2/pipeline/src/fpl_dof/sources/fetch.py)
- [`pipeline/src/fpl_dof/sources/fplarchive/adapter.py`](file:///c:/JHH/source/fpl_dof2/pipeline/src/fpl_dof/sources/fplarchive/adapter.py)
- [`.github/workflows/ingest-slow.yml`](file:///c:/JHH/source/fpl_dof2/.github/workflows/ingest-slow.yml)

#### Acceptance Criteria
- [ ] Routine full pipeline runs make zero network calls for completed prior seasons.
- [ ] Historical seasons remain fully accessible offline without relying on active network connections or remote repositories.
- [ ] Re-fetch can be explicitly forced when data cleansing or defect fixes are necessary.

### PIPE-04: Incremental Single-Gameweek Odds Acquisition (`fdcouk`)

- **Theme**: Acquisition Optimization & Politeness (Reference: `data-pipeline-design.md` §3 Catalogue & §3.5).
- **Priority**: Medium

#### Background & Problem Statement
Currently, `football-data.co.uk` odds are split across static CSVs in the prospective harness and ad-hoc scripts. Historical match odds do not change once a match is concluded, yet full-season CSV files (`E0.csv`) are often fetched in their entirety.

#### Proposed Design & Solution
1. **Formalize `fdcouk` Adapter**:
   - Convert `fdcouk` into a first-class registered source adapter ([`SourceAdapter`](file:///c:/JHH/source/fpl_dof2/pipeline/src/fpl_dof/sources/base.py)) under `pipeline/src/fpl_dof/sources/fdcouk/`.
2. **Delta / Incremental Fetching**:
   - Freeze all completed matches and past gameweeks into immutable Bronze snapshots.
   - In the weekly pre-deadline loop, fetch only the current gameweek's upcoming fixture odds.
   - Compare match timestamps to avoid downloading or re-parsing concluded matches.

#### Affected Components
- `pipeline/src/fpl_dof/sources/fdcouk/` (new adapter module)
- [`pipeline/src/fpl_dof/sources/registry.py`](file:///c:/JHH/source/fpl_dof2/pipeline/src/fpl_dof/sources/registry.py)
- [`.github/workflows/ingest-slow.yml`](file:///c:/JHH/source/fpl_dof2/.github/workflows/ingest-slow.yml) & [`.github/workflows/day-before.yml`](file:///c:/JHH/source/fpl_dof2/.github/workflows/day-before.yml)

#### Acceptance Criteria
- [ ] Pre-deadline ingestion only requests odds for active and upcoming fixtures.
- [ ] Concluded historical fixture odds remain frozen and are never re-fetched.
- [ ] Network payload size and execution duration are minimized on the weekly cadence.

### PIPE-05: Unified Historical & Live Match Odds in Gold

- **Theme**: Data Model Harmonization & Feature Parity (Reference: `data-pipeline-design.md` §3.5 & Catalogue).
- **Priority**: Medium

#### Background & Problem Statement
Currently, odds data exists in divergent formats:
- `oddsapi` outputs Shin de-vigged market expectations to `Table.TEAM_MATCH_EXPECTATION` in Silver.
- Historical `fdcouk` files store raw 1X2 bookmaker odds (Bet365, Pinnacle, etc.) in prospective CSVs.
Forecasting models (e.g. `A+odds`, model `M2`) cannot seamlessly train on historical seasons and predict on the current season without managing divergent formats and paths.

#### Proposed Design & Solution
1. **Consolidated Gold Match Odds Table (`team_match_odds`)**:
   - Combine historical `fdcouk` odds and live odds (`oddsapi` / `fdcouk`) into a single canonical Gold dataset.
2. **Standardized Representation**:
   - Columns: `season`, `gameweek`, `fixture_id`, `match_date_utc`, `home_team_code`, `away_team_code`, raw bookmaker consensus odds, and de-vigged probabilities (`home_win_prob`, `draw_prob`, `away_win_prob`, `expected_home_goals`, `expected_away_goals`, `clean_sheet_home`, `clean_sheet_away`).
3. **Universal Accessor**:
   - Expose a single query interface or Parquet dataset for both offline backtest training and live decision solving.

#### Affected Components

#### Acceptance Criteria
- [ ] Historical match odds (2023–2026) and live 2026/27 odds are accessible through an identical schema and accessor.
- [ ] All team representations use canonical, permanent team codes.
- [ ] De-vigged probabilities and expected goals are computed using a consistent mathematical formulation across all seasons.
