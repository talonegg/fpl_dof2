## DL-103 — CI's Python tests run as three shards balanced on measured time, the coverage gate beside them

**Status:** Accepted · **Date:** 2026-10-26 · **Decided by:** Owner, on the agent's review of CI's
test time (items 1 to 3), with the shard count set by the measurement below ·
**Serves:** NFR-01, NFR-09 · **Supersedes:** [DL-100](DL-100.md) item 2 (two shards, split by
module's name)

### Context

ORC-09 split the suite into two shards by a hash of each module's name. By measured time that
split was uneven: 341 test-seconds in one shard, 236 in the other, so CI waited on the heavier
(118 s against 55 s on `main`'s R1.4.3 run, the coverage gate included in the lighter). DL-100
tried a third shard on the same hash and found it slower, because the hash split three ways was
just as uneven and every shard builds the shared session fixtures again.

Measured locally on four workers (the runners' count), each shard on its own:

| Split | Shards' wall clock |
| --- | --- |
| Two, by name's hash, before the trims | 68 s (+8 s coverage gate) and 104 s |
| Two, balanced on measured time | 75 s and 77 s |
| Three, balanced on measured time | 55 s, 63 s and 54 s |

The three shards do more work between them (172 s against 152 s), the shared fixtures built once
more; the wall clock, which is what CI's feedback costs, is lower.

### Decision

1. **The suite runs as three shards**, each test module in one, assigned heaviest first to the
   lightest shard by its recorded seconds in `pipeline/tests/shard_weights.json`. A module the file
   does not name weighs the median. The plan depends on the files alone, so every shard computes
   the same one.
2. **The weights are rewritten deliberately** (`pipeline/scripts/shard_weights.py`, from a full
   run's JUnit report) when a test says the recorded split has tipped past a tenth, not on every
   run.
3. **The rules coverage gate is its own CI job**, beside the shards; the required `pipeline-test`
   check waits for both.
4. The end-to-end tests of the live gameweek build their shared opening once a run
   (`built_once`), and walk the three models the gameweek completion tests already walk.
5. The 150-second budget per shard ([DL-101](DL-101.md)) and the CI workflow's are unchanged until
   the new split has run on GitHub's runners.

### Consequences

- CI's Python tests should take about two-thirds of their former wall clock; the runners' speed
  still varies about twofold (DL-101), so the budgets are reviewed on observed runs, not these.
- One more runner per CI run, free on a public repository (NFR-01).
- A large new test module can tip the split; the balance test names it, and rewriting the weights
  is one command.
