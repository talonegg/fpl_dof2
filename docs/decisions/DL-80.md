## DL-80 — Branching and release model: feature → dev/Rx.y.z → pre-release → main, tagged per release

**Status:** Accepted · **Date:** 2026-10-18 · **Decided by:** Owner · **Serves:** NFR-09, NFR-12,
NFR-15

Superseded in part by [DL-82](DL-82.md): item 3 (feature branches merge into the dev branch directly).

### Context

Work went to one long-lived `dev` branch and reached `main` by pull request whenever it was ready;
every merge into `main` deploys, and the scheduled pipeline runs `main`'s code. Nothing distinguished a
release from any other merge, nothing tested a promotion against production data before it went live,
and short-lived branches accumulated (27 on the remote). Releases are now numbered `Rx.y.z` (DL-74).

### Decision

1. **`main` is production and carries one annotated tag per release** (`Rx.y.z`; the existing `R1.0`
   predates the scheme). Only `pre-release` merges into it, by pull request.
2. **Each release is built on `dev/Rx.y.z`**, cut from `main` when the release starts; the current one
   is `dev/R1.1.0`. The old `dev` branch became it.
3. **Features and fixes are built on `feature/<description>`**, branched from the open `dev/Rx.y.z`,
   merged back by pull request, then deleted.
4. **Promotion goes through `pre-release`**, which is `main` plus the promotion under test: it is
   brought level with `main` first, then the release branch is merged in. CI and a smoke test of the
   built site against the latest published contract (`pre-release.yml`) run there.
5. **When the pre-release checks pass,** a pull request from `pre-release` into `main` — CI and the
   smoke test required — is merged, which deploys; the merge commit is tagged, and the tag publishes
   a GitHub Release (`release.yml`).
6. **The next release** starts on a new `dev/Rx.y.z` cut from `main`, with the number incremented.
7. **Hotfixes** are built on `feature/<fix-description>` from `main`, promoted through `pre-release`
   into `main`, tagged with the patch number incremented, and deleted; `main` is then merged into the
   open `dev/Rx.y.z` so the fix is not lost.
8. **Enforcement:** `main` and `pre-release` accept changes only by pull request with passing checks,
   for administrators too. The procedure for agents is the `release` skill (`.claude/skills/release/`).
9. The release tooling itself shipped through this flow as hotfix **R1.0.1**.

### Consequences

- Pre-release checks are CI plus the site smoke test; the walk-forward backtest stays weekly
  (`backtest.yml`), not a promotion gate — a model regression is caught by the model card, not here.
- Remote branches already merged into `main` were deleted; unmerged ones were kept.
- The pipeline's state branches (`data`, `snapshots`, `ledger`) are outside this model and keep being
  written by workflows.
