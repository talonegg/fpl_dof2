## DL-82 — Feature branches merge into the release's dev branch directly, without a pull request

**Status:** Accepted · **Date:** 2026-10-20 · **Decided by:** Owner · **Serves:** NFR-09, NFR-12

Supersedes [DL-80](DL-80.md) item 3 and [DL-81](DL-81.md) item 4.

### Context

DL-80 put every `feature/*` branch through a pull request into the open `dev/Rx.y.z`, and DL-81 made
each R1.1.0 remediation item one such pull request. This project has one maintainer, so a pull
request into a dev branch reviews nothing the local checks and CI on `dev/**` do not already check:
it only adds a wait and a merge to the work. The review that matters is at promotion, where
`pre-release` and `main` stay protected.

### Decision

1. **A `feature/<description>` branch merges into the open `dev/Rx.y.z` directly** — a local merge,
   then a push of the dev branch — with no pull request.
2. **The local checks run before that push:** lint, format, type check, the Python and web tests and
   the docs check (the commands in `CLAUDE.md`). CI runs on every push to `dev/**`; a red dev branch
   is fixed before anything else lands on it.
3. **Feature branches are kept until the release closes**, then deleted, local and remote, once its
   tag exists. A merged branch shows what went into the release while it is open.
4. **Unchanged from DL-80:** promotion `dev/Rx.y.z → pre-release → main` is by pull request with
   required checks; `main` and `pre-release` are protected, for administrators too; hotfixes go
   through `pre-release`; one annotated tag per release.

### Consequences

- A defect can now reach `dev/Rx.y.z` without anyone seeing a diff first. The local checks before the
  push and the pre-release smoke test are what stand between it and `main`.
- The procedure is the `release` skill; the release register shows the flow.
