## 1. Overview & Objectives

This backlog defines technical improvements for the **FPL DOF Ingestion and Data Platform**. The initiatives focus on enhancing point-in-time fidelity (strict temporal scoping without lookahead leakage), creating unified multi-season views in Gold, eliminating redundant historical network ingress, and standardizing match odds across past and current seasons.

### PIPE-01: Season + Gameweek Temporal Scoping & Retrospective Ingress

- **Theme**: Temporal Integrity & Walk-Forward Fidelity (Reference: `data-pipeline-design.md` §1.4 & §4).
- **Priority**: High

#### Background & Problem Statement
Currently, Invariant 5 dictates that scraped aggregate sources (such as Understat and FBref) are conformed with `scope="season"` and `gameweek=None` to prevent full-season totals from masquerading as single gameweek observations. However, this creates a coarse grain: backtest models running at GW1 can either see the entire season's totals (lookahead bug) or none of it (information loss). Furthermore, when a new source is added mid-season (e.g. at GW10), there is no standardized protocol to reconstruct what was known prior to each earlier gameweek.

#### Proposed Design & Solution
1. **Granular Temporal Stamping**:
   - Refactor `Table.PLAYER_ADVANCED` and `Table.PLAYER_METRIC` to index by `season` AND `as_of_gameweek`.
   - In season `2026/27` at `GW1`, models only access information published prior to the GW1 deadline.
   - At `GW5`, models access observations prior to the GW5 deadline, containing the complete progressive history of GW1, GW2, GW3, GW4, GW5, plus all prior seasons.
2. **Backdated Retrospective Ingress for New Sources**:
   - When a new source is introduced mid-season (e.g. at GW10):
     - If the source provides timestamped match logs, map entries to the corresponding FPL gameweek deadlines:
       $$\text{GW}_k \iff T_{\text{event}} < T_{\text{deadline}}(\text{GW}_k)$$
     - If the source only exposes running totals without match logs, generate backdated best-effort snapshot estimations for GW1 through GW9 based on available historical timestamps.
     - Record the match method and provenance in `Table.PLAYER_CROSSWALK` and metadata.

#### Affected Components
- [`pipeline/src/fpl_dof/silver/tables.py`](../../../pipeline/src/fpl_dof/silver/tables.py) (`METRIC_SCOPES`, `PlayerAdvancedSchema`, `PlayerMetricSchema`)
- [`pipeline/src/fpl_dof/sources/understat/adapter.py`](../../../pipeline/src/fpl_dof/sources/understat/adapter.py)
- [`pipeline/src/fpl_dof/sources/fbref/adapter.py`](../../../pipeline/src/fpl_dof/sources/fbref/adapter.py)
- [`pipeline/src/fpl_dof/stages/transform.py`](../../../pipeline/src/fpl_dof/stages/transform.py)

#### Acceptance Criteria
- [x] No metric stamped with `as_of_gameweek = N` contains data whose event or observation timestamp was after the GW $N$ deadline. — `test_latest_as_of_ignores_what_was_fetched_after_it`
- [ ] Walk-forward simulation at GW $N$ yields identical feature vectors whether executed during GW $N$ or replayed at GW $N+10$. — REM-02 bounds the bronze read; the equality test is REM-09's
- [ ] Newly ingested sources backfill incremental snapshots for historical gameweeks with verified non-leakage tests. — REM-09: not built (DL-81)

### PIPE-02: Unified Multi-Season Player View in Gold (Archive + Cache + API)

- **Theme**: Data Unification & Long-Horizon Modeling (Reference: `data-pipeline-design.md` §3.1, §3.4 & §4).
- **Priority**: Medium-High

#### Background & Problem Statement
Currently, multi-season player history is fragmented across three separate components:
1. `fpl` adapter provides current season stats and aggregated `history_past` season summaries.
2. `fplarchive` provides granular past-season gameweek CSVs (Vaastav mirror).
3. `fplcache` holds pinned frozen deadline snapshots up to GW38 2025/26.
Downstream models and prospective harnesses must reconcile these sources ad-hoc. Furthermore, FPL re-indexes integer `player_id` (`element`) every season, creating severe risk of cross-season identity corruption if keys are conflated.

#### Proposed Design & Solution
1. **Unified Gold Player Dataset (`player_career_history`)**:
   - Establish a conformed Gold dataset combining historical gameweek actuals from `fplarchive`, frozen snapshots from `fplcache`, and live `element_summary` from the `fpl` API.
2. **Career-Stable Key Enforcement**:
   - Strictly join and index cross-season records using FPL's permanent `player_code` (`code`), never seasonal `player_id`.
   - Maintain a canonical crosswalk mapping `(season, player_id) -> player_code`.
3. **Harmonized Defensive & Metric Columns**:
   - Explicitly store Defensive Contribution components prior to 2025/26 as `null` (not zero) to uphold DL-18.
   - Standardize club identifiers across seasons using permanent team codes.

#### Affected Components
- [`pipeline/src/fpl_dof/sources/fpl/adapter.py`](../../../pipeline/src/fpl_dof/sources/fpl/adapter.py)
- [`pipeline/src/fpl_dof/sources/fplarchive/adapter.py`](../../../pipeline/src/fpl_dof/sources/fplarchive/adapter.py)
- [`pipeline/src/fpl_dof/stages/publish.py`](../../../pipeline/src/fpl_dof/stages/publish.py)
- [`pipeline/src/fpl_dof/forecast/`](../../../pipeline/src/fpl_dof/forecast/)

#### Acceptance Criteria
- [ ] A single Gold artifact or query interface yields a player's complete gameweek history across all available historical and current seasons. — REM-05: archive club codes are mapped wrongly, and nothing reads the gold
- [x] Reassigned seasonal player IDs never collide across seasons.
- [ ] Defensive metrics prior to 2025/26 remain strictly nullable. — REM-05: keyed on the partition's season, not the row's

### PIPE-03: Zero-Re-fetch Immutable Acquisition for Prior Seasons

- **Theme**: Cost Discipline & Pipeline Ingress Optimization (Reference: `data-pipeline-design.md` §3.4 & §5).
- **Priority**: Medium

#### Background & Problem Statement
Historical data from completed seasons (such as past FPL archive data) is immutable by definition. While `fplarchive` currently specifies a 1-year cache TTL (`_YEAR`), network checks or full re-runs can still trigger redundant file requests or depend on external GitHub mirrors during local or CI runs.

#### Proposed Design & Solution
1. **Permanent Frozen Bronze Tiers**:
   - Mark finished historical seasons as permanently frozen (`immutable=True` on `Resource` or `IngestRequest`).
   - Store historical archive data in a committed or persistent storage partition (`data/bronze/archive/`) that bypasses TTL expiration.
2. **Explicit Re-acquisition Guard**:
   - Ingestion bypasses network checks entirely for frozen seasons unless an explicit `--rebackfill` or `--fix-defect` flag is supplied.
   - Eliminates external mirror availability risks during ordinary weekly pipeline runs.

#### Affected Components
- [`pipeline/src/fpl_dof/sources/base.py`](../../../pipeline/src/fpl_dof/sources/base.py) (`Resource`, `IngestRequest`)
- [`pipeline/src/fpl_dof/sources/fetch.py`](../../../pipeline/src/fpl_dof/sources/fetch.py)
- [`pipeline/src/fpl_dof/sources/fplarchive/adapter.py`](../../../pipeline/src/fpl_dof/sources/fplarchive/adapter.py)
- [`.github/workflows/ingest-slow.yml`](../../../.github/workflows/ingest-slow.yml)

#### Acceptance Criteria
- [ ] Routine full pipeline runs make zero network calls for completed prior seasons. — REM-10: CI prunes archive bronze with the rolling window
- [ ] Historical seasons remain fully accessible offline without relying on active network connections or remote repositories. — REM-10
- [ ] Re-fetch can be explicitly forced when data cleansing or defect fixes are necessary. — REM-10: `--rebackfill` still sends conditional headers, and a 304 re-blesses the old bytes

### PIPE-04: Incremental Single-Gameweek Odds Acquisition (`fdcouk`)

- **Theme**: Acquisition Optimization & Politeness (Reference: `data-pipeline-design.md` §3 Catalogue & §3.5).
- **Priority**: Medium

#### Background & Problem Statement
Currently, `football-data.co.uk` odds are split across static CSVs in the prospective harness and ad-hoc scripts. Historical match odds do not change once a match is concluded, yet full-season CSV files (`E0.csv`) are often fetched in their entirety.

#### Proposed Design & Solution
1. **Formalize `fdcouk` Adapter**:
   - Convert `fdcouk` into a first-class registered source adapter ([`SourceAdapter`](../../../pipeline/src/fpl_dof/sources/base.py)) under `pipeline/src/fpl_dof/sources/fdcouk/`.
2. **Delta / Incremental Fetching**:
   - Freeze all completed matches and past gameweeks into immutable Bronze snapshots.
   - In the weekly pre-deadline loop, fetch only the current gameweek's upcoming fixture odds.
   - Compare match timestamps to avoid downloading or re-parsing concluded matches.

#### Affected Components

#### Acceptance Criteria
- [ ] Pre-deadline ingestion only requests odds for active and upcoming fixtures. — REM-07: the adapter is off and nothing ingests it
- [ ] Concluded historical fixture odds remain frozen and are never re-fetched. — REM-07
- [ ] Network payload size and execution duration are minimized on the weekly cadence. — REM-07

### PIPE-05: Unified Historical & Live Match Odds in Gold

- **Theme**: Data Model Harmonization & Feature Parity (Reference: `data-pipeline-design.md` §3.5 & Catalogue).
- **Priority**: Medium

#### Background & Problem Statement
Currently, odds data exists in divergent formats:
- `oddsapi` outputs Shin de-vigged market expectations to `Table.TEAM_MATCH_EXPECTATION` in Silver.
- Historical `fdcouk` files store raw 1X2 bookmaker odds (Bet365, Pinnacle, etc.) in prospective CSVs.
Forecasting models (e.g. `A+odds`, model `M2`) cannot seamlessly train on historical seasons and predict on the current season without managing divergent formats and paths.

#### Proposed Design & Solution
1. **Consolidated Gold Match Odds Table (`team_match_odds`)**:
   - Combine historical `fdcouk` odds and live odds (`oddsapi` / `fdcouk`) into a single canonical Gold dataset.
2. **Standardized Representation**:
   - Columns: `season`, `gameweek`, `fixture_id`, `match_date_utc`, `home_team_code`, `away_team_code`, raw bookmaker consensus odds, and de-vigged probabilities (`home_win_prob`, `draw_prob`, `away_win_prob`, `expected_home_goals`, `expected_away_goals`, `clean_sheet_home`, `clean_sheet_away`).
3. **Universal Accessor**:
   - Expose a single query interface or Parquet dataset for both offline backtest training and live decision solving.

#### Affected Components
- [`pipeline/src/fpl_dof/silver/tables.py`](../../../pipeline/src/fpl_dof/silver/tables.py)
- [`pipeline/src/fpl_dof/sources/oddsapi/market.py`](../../../pipeline/src/fpl_dof/sources/oddsapi/market.py)
- [`pipeline/src/fpl_dof/stages/publish.py`](../../../pipeline/src/fpl_dof/stages/publish.py)
- [`pipeline/src/fpl_dof/forecast/models/`](../../../pipeline/src/fpl_dof/forecast/)

#### Acceptance Criteria
- [ ] Historical match odds (2023–2026) and live 2026/27 odds are accessible through an identical schema and accessor. — REM-06: no `captured_at`; historical rows have no gameweek
- [ ] All team representations use canonical, permanent team codes. — REM-05
- [x] De-vigged probabilities and expected goals are computed using a consistent mathematical formulation across all seasons.

### PIPE-06: Accumulating Silver Parquet Persistence & Replay Utility

- **Theme**: State Persistence & Historical Feature Continuity (Reference: `data-pipeline-design.md` §5.1, §5.2).
- **Priority**: High

#### Background & Problem Statement
Currently, [`pipeline/src/fpl_dof/stages/transform.py`](../../../pipeline/src/fpl_dof/stages/transform.py) defines accumulating tables (`APPENDED = frozenset({Table.PRICE_HISTORY, Table.PLAYER_GAMEWEEK})`), and [`append_table()`](../../../pipeline/src/fpl_dof/silver/store.py) merges new observations with existing Parquet files. However, [`rebuild_rolling_branch()`](../../../pipeline/scripts/retention.py) only stages `bronze/` to the `data` git branch. On CI runners, `data/silver/` starts completely empty on every invocation. As a result, `price_history.parquet` only retains the single observation from the current run, destroying daily price-momentum and ownership-trend histories needed by downstream forecasting models.

#### Proposed Design & Solution
1. **Persist Accumulating Silver Partitions**:
   - Update [`pipeline/scripts/retention.py`](../../../pipeline/scripts/retention.py) to stage and commit `data/silver/season=*/price_history.parquet` to the `data` branch alongside the rolling `bronze/` tree.
2. **Deterministic Bronze-to-Silver Price Replay**:
   - Implement `fpl-dof silver replay-prices`: a pure replay utility that iterates through all retained `bootstrap_static` Bronze snapshots in chronological order, extracting the price and ownership vectors and rebuilding `price_history.parquet` deterministically (DP-11) whenever the Silver store is initialized or repaired.

#### Affected Components
- [`pipeline/scripts/retention.py`](../../../pipeline/scripts/retention.py)
- [`pipeline/src/fpl_dof/silver/store.py`](../../../pipeline/src/fpl_dof/silver/store.py)
- [`pipeline/src/fpl_dof/cli.py`](../../../pipeline/src/fpl_dof/cli.py)
- [`.github/workflows/ingest-fast.yml`](../../../.github/workflows/ingest-fast.yml) & [`.github/workflows/pipeline.yml`](../../../.github/workflows/pipeline.yml)

#### Acceptance Criteria
- [x] `price_history.parquet` retains observations across successive CI workflow runs on GitHub Actions. — `test_rebuild_rolling_branch_never_drops_what_another_run_pushed`
- [x] `fpl-dof silver replay-prices` reconstructs identical Parquet rows from historical Bronze snapshots with byte-level determinism. — `test_transform_and_replay_write_the_same_price_rows`
- [x] Running a full rebuild from scratch does not lose previously captured price changes within the retention window.

#### Widened by DL-79 — one restore step (03 §12 O3, O4)
- The branch restore copied across `ingest-fast.yml`, `ingest-slow.yml` and `pipeline.yml` becomes
  one composite action or `retention.py restore`, used by every workflow, before silver joins what it
  restores. The retention window is read from configuration, not repeated in YAML.
- [ ] One restore implementation; the retention window is defined once. — REM-10: a hard-coded fallback window remains

### PIPE-07: Conditional HTTP Ingress (ETags & 304 Not Modified)

- **Theme**: Ingress Optimization, Bandwidth & Runner Cost Reduction (Reference: `data-pipeline-design.md` §2.1, §5.2).
- **Priority**: Medium-High

#### Background & Problem Statement
[`Fetcher.fetch()`](../../../pipeline/src/fpl_dof/sources/fetch.py) currently relies entirely on client-side TTL. When a resource expires, `Fetcher` executes an unconditional HTTP `GET`, downloading the complete multi-megabyte payload (e.g. 5MB `bootstrap-static`, `element_summary`, GitHub archives, and Odds API) even when the upstream data has not changed. FPL's CloudFront CDN and GitHub both support HTTP `ETag` and `Last-Modified` headers.

#### Proposed Design & Solution
1. **Header Tracking in Snapshot Metadata**:
   - Extend [`SnapshotMeta`](../../../pipeline/src/fpl_dof/sources/bronze.py) with optional `etag: str | None = None` and `last_modified: str | None = None`.
2. **Conditional Header Dispatch**:
   - In [`Fetcher._request_with_retries()`](../../../pipeline/src/fpl_dof/sources/fetch.py), if an expired snapshot exists, send `If-None-Match` and `If-Modified-Since`.
3. **HTTP 304 Fast-Path Handling**:
   - When the server responds with `HTTP 304 Not Modified`:
     - Avoid downloading payload bytes or recomputing SHA-256 hashes.
     - Either touch/extend the existing Bronze snapshot's validity or emit a lightweight 304 marker sidecar.
     - Treat the request as a zero-byte fetch, saving runner network transfer and execution duration.

#### Affected Components
- [`pipeline/src/fpl_dof/sources/bronze.py`](../../../pipeline/src/fpl_dof/sources/bronze.py) (`SnapshotMeta`)
- [`pipeline/src/fpl_dof/sources/fetch.py`](../../../pipeline/src/fpl_dof/sources/fetch.py) (`Fetcher`)

#### Acceptance Criteria
- [x] `Fetcher` sends `If-None-Match` when an earlier snapshot contains an ETag.
- [x] Upstream `HTTP 304` responses do not download payload bodies and increment a `fetcher.conditional_hits` counter.
- [x] Bronze lineage correctly records the verification timestamp without payload byte duplication.

### PIPE-08: Ingestion Schema Drift Canary & Early Detection Gate

- **Theme**: Defensive Ingestion & Early Failure Detection (Reference: `data-pipeline-design.md` §1 Invariant 7, §3.1).
- **Priority**: Medium

#### Background & Problem Statement
Currently, structural contract drift in external feeds (such as FPL moving endpoints like `team/set-piece-notes/` or modifying JSON dictionary keys) is only caught downstream during `transform.py` or when Pandera schema validation fails. If schema drift occurs, `ingest` succeeds blindly, writing invalid snapshots into Bronze and causing failures late in the pipeline after multi-minute runs.

#### Proposed Design & Solution
1. **Lightweight Ingress Canary**:
   - Add a pre-ingest or post-ingest contract canary in [`fpl_dof.sources.fpl.adapter`](../../../pipeline/src/fpl_dof/sources/fpl/adapter.py) and [`pipeline/src/fpl_dof/stages/ingest.py`](../../../pipeline/src/fpl_dof/stages/ingest.py).
   - Validate critical structural anchors in `bootstrap_static` and `fixtures` before commencing expensive per-player sweeps.
2. **Actionable Structural Diff Logging**:
   - When an expected JSON key or type changes, generate a concise schema diff in logs, identifying the exact drifted fields before unparseable bytes propagate downstream.

#### Affected Components
- [`pipeline/src/fpl_dof/sources/base.py`](../../../pipeline/src/fpl_dof/sources/base.py)
- [`pipeline/src/fpl_dof/sources/fpl/adapter.py`](../../../pipeline/src/fpl_dof/sources/fpl/adapter.py)
- [`pipeline/src/fpl_dof/stages/ingest.py`](../../../pipeline/src/fpl_dof/stages/ingest.py)

#### Acceptance Criteria
- [x] Missing or renamed root keys in `bootstrap_static` halt `ingest` immediately before launching per-player fetches.
- [x] Structural drift errors produce a diagnostic diff of expected vs received keys in the pipeline log and run manifest.

### PIPE-09: The Odds API Off by Default (Scrapers Stay Dormant)

- **Theme**: Ingress hygiene. **Priority**: High (Phase 1 quick win). Narrowed by
  [DL-79](../../decisions/DL-79.md).

#### Background
Understat and FBref are already off by default (`enabled_by_default = False`) and no workflow
enables them; both are blocked upstream (D-23). The Odds API is enabled by default in
`config/defaults/sources.yaml`, degrades cleanly without `ODDS_API_KEY`, is credit-capped with no
history (D-20), and is not used by the model (DL-59, DL-60). Odds come from football-data.co.uk
(PIPE-04, PIPE-05).

#### Proposed Design
- Remove the `oddsapi` override from `config/defaults/sources.yaml`, so it is off by default like the
  scrapers; record the change on `/health` as "off by configuration".
- Keep the Understat and FBref adapters, dormant and off, in case access returns. Retained bronze stays
  replayable (DP-11).

#### Affected Components
- [`pipeline/src/fpl_dof/config/defaults/sources.yaml`](../../../pipeline/src/fpl_dof/config/defaults/sources.yaml)
- `pipeline/tests/test_external_sources.py` (default-enablement expectations)

#### Acceptance Criteria
- [x] A default run makes no request to Understat, FBref or The Odds API.
- [x] `/health` shows all three as off by configuration, not as failing.

### PIPE-10: Automated Temporal Non-Leakage Quality Gate (Invariant 5)

#### Affected Components

- [x] Gate failure report details the exact violating entity, timestamp, and deadline.

### PIPE-11: Bronze Store Integrity Audit & Snapshot Hygiene Tooling

- **Theme**: Operational Verification & Bronze Resiliency (Reference: `data-pipeline-design.md` §2.2, §5.2).
- **Priority**: Low-Medium

#### Background & Problem Statement
Bronze snapshots rely on twin artifacts (`.json.gz` payload + `.meta.json` lineage sidecar). Torn writes during aborted CI runs or git worktree checkouts can leave orphaned payload files or corrupted archives. Currently, `bronze.latest()` skips missing metadata, but corrupted gzip archives or checksum mismatches crash downstream transform stages unexpectedly.

#### Proposed Design & Solution
1. **Bronze Audit CLI Command (`fpl-dof bronze verify`)**:
   - Provide a CLI diagnostic tool that inspects the Bronze store:
     - Verifies uncompressed byte SHA-256 against `meta.sha256`.
     - Tests gzip decompression integrity.
     - Detects orphaned payloads lacking metadata sidecars and orphaned sidecars lacking payloads.
     - Flags invalid or unparseable directory date structures.
2. **Automated Clean / Quarantine Option (`--prune-orphans`)**:
   - Safely removes or quarantines corrupt/torn snapshots without affecting valid historical partitions.

#### Affected Components
- [`pipeline/src/fpl_dof/cli.py`](../../../pipeline/src/fpl_dof/cli.py)
- [`pipeline/src/fpl_dof/sources/bronze.py`](../../../pipeline/src/fpl_dof/sources/bronze.py)

#### Acceptance Criteria
- [x] `fpl-dof bronze verify` reports accurate pass/fail counts for snapshot integrity across all sources.
- [ ] Checksum corruption or torn files are flagged with exact file paths before `transform` runs. — REM-10: `bronze verify` runs by hand only

### PIPE-12: One Clock and One Current Gameweek per Run

- **Theme**: Temporal integrity (03 §12 P4). **Priority**: High — a prerequisite for PIPE-01 and
  PIPE-10. Added by [DL-79](../../decisions/DL-79.md).

#### Background
`utcnow()` is read eight times across the stages, and three definitions of "the next gameweek" are in
use: first unfinished (`forecast/live.py`, `forecast/xp_v0.py`), first deadline after now
(`week/cadence.py`), and FPL's `is_next` (`stages/publish.py`). Between a deadline passing and the
gameweek finishing, the published `xp_next` may describe a different gameweek from the advice.

#### Proposed Design
- `StageContext.as_of` is set once in `cli.py` and recorded in the manifest; stages and core read it,
  never the wall clock.
- One `current_gameweek(gameweeks, as_of)` used by forecast, week, decision and publish.

#### Acceptance Criteria

### PIPE-14: Permanent Bronze Archive Actually Written

- **Theme**: Reproducibility evidence (NFR-06, FR-05, DP-11). **Priority**: High — evidence is being
  lost every day it is not fixed. Added 2026-10-18.

#### Background & Problem Statement
The `snapshots` branch — one permanent bronze tarball per gameweek, the NFR-06 evidence trail
(architecture §7.3) — **has never been written**. Every `ingest-slow.yml` run logs *"no current
gameweek known yet; skipping the permanent archive for this run"*, and the branch does not exist on
the remote. The archive step takes the gameweek from `fpl-dof-schedule`, which reads it from the
**silver** `gameweek` table (`schedule_cli.py`, `time_to_deadline`); the slow-ingest job runs ingest
only, and silver is not persisted between CI runs (PIPE-06), so the gameweek is always unknown.
Bronze older than the ~30-day rolling window on `data` has therefore been discarded since GW1.

#### Proposed Design & Solution
1. Key the archive on a gameweek that ingest can know by itself: read it from the bronze
   `bootstrap-static` snapshot just written (the event that is current, else next), or have the step
   run after a transform. Prefer the former — the archive must not depend on silver.
2. A run that cannot determine the gameweek **fails the step visibly** (an alert), rather than
   skipping with a log line nobody reads (DP-15: degraded state is visible).
3. Recover what still exists: archive the gameweeks still inside the rolling window on `data` once,
   and record in the snapshot index which gameweeks were lost.

#### Affected Components
- [`.github/workflows/ingest-slow.yml`](../../../.github/workflows/ingest-slow.yml) (the archive step)
- [`pipeline/scripts/retention.py`](../../../pipeline/scripts/retention.py) (`append_permanent_snapshot`)
- [`pipeline/src/fpl_dof/schedule_cli.py`](../../../pipeline/src/fpl_dof/schedule_cli.py) or a bronze-only gameweek helper

#### Acceptance Criteria
- [ ] The `snapshots` branch exists and gains one tarball per gameweek from the next slow ingest on. — REM-04 built; ticked when the first slow ingest on `main` writes the branch
- [x] A slow ingest that cannot determine the gameweek fails and alerts; none skips silently. — `test_archive_bronze_by_gameweek_fails_without_a_schedule`
- [x] The gameweeks still within the rolling window are archived once; the lost ones are recorded. — `test_archive_bronze_by_gameweek_writes_once_and_records_losses`

## 4. Remediation Plan

The build was reviewed against §2 on 2026-10-19 and reopened ([DL-81](../../decisions/DL-81.md)).
Each item below is one `feature/*` branch merged into `dev/R1.1.0` (DL-82), taken in this
order; each closes the unticked boxes that name it. An item is done when its boxes are ticked and
each ticked box names the test that proves it.

### 4.1 Items

#### REM-01: Green build and the replay crash (PIPE-13)
- `ruff format` clean; `mypy` clean across all eight failing files.
- `forecast/fit.py`'s `_predict_replay`: pass `fixture_index_from_history(history, season, horizon)`
  in the declared order; build identity and features from the replayed season only, as before.
- `decision/replay.py` treats a fold that cannot be fitted (`ColdStartError`, no features) as it
  treated `InfeasibleError`: log it and move on, never abort the replay.
- A fast test drives `fit_as_of(...).predict(..., history=, season=)` on a fixture, so the replay
  path is no longer reached only by `--slow`.

#### REM-04: The permanent archive, once per gameweek (PIPE-14) — built
- Write a gameweek's tarball once: if `bronze-full/<season>/gwNN.tar.gz` exists, skip; never overwrite it.
- Distinguish "no gameweek ahead" (season over, or not yet published), which is a known state and
  logs a notice, from "the gameweek cannot be read", which fails and alerts.
- The lost-gameweeks note in `index.json` is written for the `snapshots` branch only, never `ledger`.
- Recover once: archive the gameweeks still inside the rolling window on `data`, and record the
  lost ones in the index.
- Ships with R1.1.0, not as a hotfix (DL-81); it takes effect when the release reaches `main`.

#### REM-02: Price history and `--as-of` (PIPE-01, PIPE-06, PIPE-12) — built
- Price rows carry the snapshot's `fetched_at`, in transform and in `silver replay-prices` alike,
  so a re-run adds nothing and a replay reproduces what live runs wrote.
- `append_table` sorts on its keys on every write.
- `--as-of` bounds what is read: `BronzeStore.latest()` takes an `as_of` and ignores later snapshots.
  `ingest` refuses `--as-of`; it fetches now, stamped now.
- `--as-of` sets `ctx.as_of` and no longer freezes `utcnow()`, so the manifest's start and finish
  times stay real; `FPL_DOF_AS_OF` remains only as the test suite's clock. `quality/rules.py` loses
  its wall-clock fallback.

#### REM-03: No push to `data` drops another's (PIPE-06) — built
- `retention.py rolling` folds in what `data` holds just before pushing (bronze by file, price rows
  by key) and force-pushes with a lease on that commit, retrying if another workflow pushed in
  between. Not a shared concurrency group: GitHub cancels a *pending* run in a group when a newer
  one queues, so an hourly `ingest-fast` could cancel a pre-deadline `pipeline` run.

#### REM-05: Club codes in gold from data, by row (PIPE-02, PIPE-05)
- Silver `team` carries the FPL team `code`; gold maps season-local ids to codes from it, per row's
  `season`, and `TEAM_ID_TO_CODE_2627` is deleted.
- The DL-18 nulling keys on the row's `season`.
- Tests write the real layout: every season in the current season's partition.
- `transform` builds gold. Its first consumer comes in R1.2 (DL-81); until then gold is built and
  tested, not read.

#### REM-06: Odds behind the adapter (PIPE-04, PIPE-05)
- The football-data.co.uk CSV format (`Div`, `HomeTeam`, `B365H`, `AvgH`, file-name season codes) is
  parsed only in `sources/fdcouk/`, conformed into silver; gold reads silver and nothing else.
- Odds keep `captured_at`; gold takes the latest capture before the fixture's deadline, not the first
  row found. A missing Bet365 price falls back to the average.
- `test_source_isolation.py` also fails on adapter internals re-exported from the `sources` root.
- `day_before_gate.py`, `prospective_ci.py` and `score_xp.py` read the FPL API through the `fpl`
  adapter and bronze, and the isolation test's allow-list is deleted (DL-81).

#### REM-07: The prospective odds feed (PIPE-04)
- The prospective run ingests football-data.co.uk through the adapter before `plan`, enabled for
  that run, and records `data/bronze/fdcouk` again.
- `fetch_fixtures_csv` returns text; the `/health` descriptor returns, and the adapter's disabled
  reason says what is true.

#### REM-08: Forecast behaviour restored (PIPE-12, PIPE-13)
- Training stops at the last *finished* gameweek; a half-played gameweek never enters a fit (DL-81).
- With no current-season rows before the deadline, team strength is league average, as before;
  never last season's codes looked up by this season's ids.
- The cold-start fallback (`xp_v0`) writes `captain_score`, so the default captain rule holds.
- One `current_gameweek` predicate for forecast, week, decision, publish and the day-before gate.
- A test fails if a stage or core module calls `utcnow()` rather than reading `ctx.as_of`.
- Tests: a fixture between a deadline and the gameweek finishing yields one gameweek across
  `players.json`, `week.json` and `plan.json`; live and backtest give identical predictions for one
  fold through `fit_as_of`, and the backtest calls it.

#### REM-09: The look-ahead gate on real tables (PIPE-01, PIPE-10)
- The gate checks columns the strict schemas have: `kickoff_time` against the gameweek deadline in
  `player_gameweek`, `as_of_gameweek` against capture time in the metric tables. Its tests build
  schema-valid frames.
- A test replays GW N's features at a later as-of time and gets the same vectors.
- Retrospective ingress for a source added mid-season (DL-81): timestamped match logs map to the
  first deadline after each event; a source with running totals only is backdated best-effort; the
  method and provenance are recorded in `PLAYER_CROSSWALK`. Proven on recorded fixtures, since no
  live source needs it yet.

#### REM-10: Smaller defects (PIPE-03, PIPE-06, PIPE-07, PIPE-09, PIPE-11)

- The retention window is read from configuration only: no fallback literal, no hand-synced comment.
- `ingest-slow.yml` stops passing `ODDS_API_KEY`. The manifest schema version is bumped for `as_of`.
