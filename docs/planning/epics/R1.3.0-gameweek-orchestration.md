**Target Release**: R1.3.0, in two drops (§1)

## 1. Overview

The advice keeps up with the data, and every finished gameweek is judged once, on the owner's real
squad, by one scorer. R1.2.x left the decision engine able to advise every strategy on one snapshot
(MOD-04); what it did not touch is when a run happens, what a run is allowed to overwrite, and how a
gameweek is judged afterwards.

**Where it starts** (survey of 2026-10-23):

- **Runs chain by names and clocks.** `pipeline.yml` follows `Ingest (slow)` by `workflow_run`,
  `deploy.yml` follows `Pipeline`, and both match `[day-before` titles and cron strings. A fast
  ingest fetches prices, status and football-data.co.uk's `fixtures.csv` within the deadline window,
  but starts no run: what it fetched waits for the next scheduled pipeline offset (D-35).
- **The record is the last write.** `week/ledger.py` `record_advice` rewrites `advice/gwNN.json` on
  every run, so a later run in which a strategy fails replaces its earlier success with "no advice".
- **Deploy can redeploy old data.** It fires on every `Pipeline` completion, including guard-only
  runs, and falls back to the newest run that left a contract.
- **Judging is recomputed, partial and approximate.** The season log rebuilds every gameweek on
  every publish, charges no hits (D-30), and solves the hindsight optimum on placeholder prices and
  clubs (D-31, waived by [DL-93](../../decisions/DL-93.md)). Nothing records each strategy's
  player-level xP, so live xP accuracy cannot be computed; `xp_accuracy.json` and the models history
  are checked-in files built outside the repository.

```
┌──────────┬──────────────────────────────────────────────────────────┬─────────────┐
│ Item     │ Title                                                    │ Module      │
├──────────┼──────────────────────────────────────────────────────────┼─────────────┤
│ Drop A — advice that keeps up                                                     │
│ ORC-03   │ Advice of record; deploy only when a run published       │ Orchestrator│
│ ORC-08   │ Record what each strategy predicted                      │ Orchestrator│
│ ORC-01   │ Gameweek state                                           │ Orchestrator│
│ ORC-09   │ Faster pipeline runs, CI and tests                       │ All         │
│ ORC-02   │ Change manifest and typed dispatch                       │ Orchestrator│
│ ORC-07   │ Source availability alerts in the app                    │ Orch./Web   │
├──────────┼──────────────────────────────────────────────────────────┼─────────────┤
│ Drop B — every gameweek judged once                                               │
│ ORC-04   │ One realised-points scorer                               │ Core        │
│ ORC-05   │ Evaluation step and season log from evaluations          │ Orchestrator│
│ ORC-06   │ Reproducible models history                              │ Factory     │
└──────────┴──────────────────────────────────────────────────────────┴─────────────┘
```

**Order.** ORC-03 first: ORC-02 multiplies the number of runs per gameweek, and every extra run is
another chance to overwrite a good record. ORC-08 next, because every gameweek that passes without it
is a gameweek ORC-05 can never score live. ORC-09 before ORC-02: a dispatched run must finish well
inside the freeze, and more runs multiply every minute a run takes. Drop B lands before the GW13 promotion read on A and
A_odds ([E8 §5](E8-ongoing-in-season-monitoring.md)), which should be read from evaluations, not
from the recomputed log. Drop B takes the next free patch number when it is cut, as R1.2.2 did
([DL-87](../../decisions/DL-87.md)).

**Debt repaid**: D-30 and D-31 (ORC-04, ORC-05), D-32 (ORC-06), D-35 (ORC-02, ORC-07); D-33 is
placed by Q8. D-34 is a recheck, not a story: it is read from ORC-08's first records.

## 2. Drop A — advice that keeps up

### ORC-03: Advice of record; deploy only when a run published

- **Absorbs**: 03 §12 O1.

#### Problem
The last run before the deadline wins whether it succeeded or not, and nothing stops a write after
the deadline. Deploy runs on every pipeline completion and may publish an older contract.

#### Design
1. **A strategy's entry in `advice/gwNN.json` is replaced only by a newer success.** A later
   failure is recorded beside it (`last_failure {as_of, reason}`) and the earlier success stays the
   advice of record (Q1). A strategy with no success before the deadline records "no advice" with
   its reason, fail-closed, as today.
2. **The record closes at the deadline.** A write for gameweek N after N's deadline is refused, not
   merely avoided because `week` has moved on.
3. **Every advice is stamped** with its snapshot's `as_of` and the run's `trigger` (`schedule`,
   `change:<kinds>`, `manual`, `day-before`), in `meta` and per strategy; the app's "As at" line
   shows both.
4. **Deploy is the last job of `pipeline.yml`, run only when that run published.** The
   `workflow_run` on `Pipeline` and the fallback search for an older contract go. `push: main`
   keeps deploying web changes until WEB-01.

#### Acceptance criteria
- [ ] A run in which a strategy fails after an earlier success leaves the success as the record and
  notes the failure.
- [ ] A write after the deadline is refused, with a test on the ledger writer.
- [ ] A guard-only or failed pipeline run deploys nothing; a published run deploys its own contract.
- [ ] `week.json`, every strategy file and `models.json` carry `as_of` and `trigger`; the header
  shows them.

### ORC-08: Record what each strategy predicted

#### Problem
`advice/gwNN.json` holds each strategy's XI and moves, not its player-level xP, so ORC-05 cannot
measure xP accuracy for a live gameweek and D-34 cannot be checked from the record.

#### Design
With each advice write, each strategy's full-pool forecast for the gameweek being decided (player,
mean, variance, P(plays)) goes to `ledger:predictions/gwNN/<strategy>.parquet`, under ORC-03's
replace-only-on-success rule. The pipeline restores it as it restores `advice/`.

#### Acceptance criteria
- [ ] Every strategy that advised has a predictions file for the gameweek, matching the frame it
  advised from, and the record of a failed strategy keeps its last successful predictions.
- [ ] The file's size per gameweek is stated in the commit; it stays within the ledger's budget.

### ORC-01: Gameweek state

#### Design
1. **The state is derived, never stored**: `gameweek_state(gw, silver, ledger, now)` in
   `gameweek.py`, beside the one definition of the gameweek being decided. Open before the
   deadline; Recorded from the deadline; Playing from the first kick-off; Finished when FPL marks it
   finished and data-checked; Evaluated once `evaluation/gwNN.json` exists for the current scorer
   version.
2. **Each run asks the state what to do**: Open refreshes every strategy; Recorded and Playing do
   nothing beyond ingest; Finished runs ORC-05; Evaluated does nothing.
3. **The chip in force** for each of the owner's gameweeks is part of the state, from entry history,
   so a Free Hit gameweek can be recognised (D-33, Q8).
4. Exactly one gameweek is Open at a time, the next deadline's; a blank or postponed fixture changes
   a gameweek's fixtures, not its state.

#### Acceptance criteria
- [ ] Every transition is covered by a test on fixture data, including a gameweek with a postponed
  fixture and the season's last gameweek.
- [ ] No stage decides "should I run" from the clock alone; each reads the state.

### ORC-09: Faster pipeline runs, CI and tests

#### Problem
Measured on 2026-10-23 (production run 39945780816, CI run 39950483642; figures in the commit):

- **The chip plan dominates the pipeline run.** The week stage solves 22 horizon scenarios (no
  chip, then each chip in each gameweek) one after another, most of the stage's time.
- **Every Python job installs with `pip`**, the pipeline's `guard` job installs the whole package
  just to decide whether to run, and the `run` job installs the `[dev]` extras it never uses.
- **The Python tests run in one process.** The slowest are module-level fits repeated across tests
  (`test_monolith.py`, `test_decide.py`, `test_a.py`, `test_a_odds.py`); the rest is a long tail.
- **The weekly backtest** walks every strategy in sequence.

#### Design
1. **Chip scenarios are solved in parallel** across the runner's cores, each an independent MILP
   from the same inputs, so the plan is identical; the worker count is `optimise` config (DP-06).
   Neither the gap nor a time limit changes: that would change the advice, and would be a model
   change with its own falsifier.
2. **Installs use `uv`** against `requirements.lock`, with its cache; `guard` installs only what
   the schedule decision imports; `run` installs no `[dev]` extras.
3. **Tests run in parallel** (`pytest-xdist`, free, pinned in the lock, Q9). The expensive fixtures
   (strategy fits, the decide snapshot) are built once per session, not per test, and every test
   stays independent of order and worker.
4. **The backtest grades strategies in parallel**, one process per strategy, each with its own
   folds, so a failure in one is isolated (D-32, ORC-06).
5. **Budgets are tested, not remembered**: a CI step fails when a pipeline run, the CI workflow or
   the Python tests exceed their budget in `schedule` config: 5 minutes, 3 minutes and 90 seconds (Q9), so a slow change is seen when it
   lands.

#### Acceptance criteria
- [ ] The parallel chip plan equals the sequential one on the golden snapshot
  (`test_golden_artefacts.py`, unchanged).
- [ ] A pipeline run, the CI workflow and the Python tests each finish within their budget; the
  before and after times are in the commit.
- [ ] The Python tests pass in parallel and in a random order.

### ORC-02: Change manifest and typed dispatch

- **Absorbs**: 03 §12 O2, F2.

#### Design
1. **The change manifest.** Ingest restores the `data` branch before it fetches, so it compares the
   new bronze with the restored copy and writes what moved: prices, status and news, fixtures
   (kick-off, gameweek), and odds for the Open gameweek. Freshness is each resource's sidecar
   `fetched_at`. No new durable store is needed.
2. **Material changes dispatch the pipeline.** Thresholds are `schedule` config (Q2). The fast and
   slow ingest end with `gh workflow run pipeline.yml` and typed inputs: `trigger`, `kinds`,
   `gameweek`, `must_publish`. The guard step validates them and refuses unknown values.
3. **The guard covers every trigger.** The freeze and the no-op rule apply to a dispatched run too;
   today dispatch bypasses the guard.
4. **One scheduled tick** replaces the three pipeline crons and the `workflow_run` on
   `Ingest (slow)`. It asks ORC-01's state whether anything is due. The day-before path becomes
   `must_publish=true`, not a title marker.
5. **A workflow test pins the wiring**: no `workflow_run`, no workflow name, title or cron string
   matched in any step.

#### Acceptance criteria
- [ ] A price change, a status change, a fixture move and new odds rows each produce the right
  manifest entry on fixture bronze, and nothing else does.
- [ ] An ingest with a material change dispatches one pipeline run with valid inputs; one without
  dispatches none; a dispatch inside the freeze is refused.
- [ ] The workflow test passes and the day-before path still fails closed.

### ORC-07: Source availability alerts in the app

- **Absorbs**: D-35.

#### Design
1. **Offline.** When a published strategy has no advice for the Open gameweek because a source it
   needs is unavailable, `models.json`'s availability names the source (from the strategy's
   `requires` and the source registry's metadata, so nothing outside `sources/` names a source,
   Invariant 1), since when, and when it is next checked. The app shows a banner on every page, not
   only on Models, until the strategy advises or the deadline passes.
2. **Arrived.** When a strategy offline in the previous record for this gameweek advises in a run
   triggered by its source's change, the app shows that the source arrived and when, and that the
   strategy was refreshed with it. The previous state comes from the ledger record (ORC-03), so
   nothing extra is stored.
3. **Late sources are checked often enough to matter.** `fixtures.csv` is already a fast-path
   resource, fetched by every fast ingest within `schedule.fast_ingest_deadline_window_hours`; its
   arrival reaches the advice through ORC-02's dispatch. The fetch cadence in the final hours is Q3.
4. **Published, never fetched by the browser** (Invariant 8): the alerts are fields of the contract,
   additive in `v1`.

#### Acceptance criteria
- [ ] A fixture run in which A_odds lacks odds shows the offline banner on every route, naming the
  source and the next check.
- [ ] A following run triggered by new odds shows the arrival and A_odds' advice; the banner goes.
- [ ] Accessibility and offline checks pass (`verify:browser`).

## 3. Drop B — every gameweek judged once

### ORC-04: One realised-points scorer

#### Problem
Realised points are computed by `week/score_advice.py` `score_lineup` in the repository and by an
outside-repository simulator for the models history, and the season log's played row charges no hits
(D-30: GW4 shows 83 where FPL gave 79).

#### Design
1. **One scorer in `rules/`**, logical core, under the rules coverage gate (100%): auto-substitutions
   (goalkeeper, formation, bench order, a player with no fixture counts as no minutes), double
   gameweeks, captain and vice-captain, the chips (Q4) and hits.
2. **The corpus is FPL's own scoring**: real public entries (the owner's gameweeks and the
   mini-league's), each with FPL's `event_points` and `event_transfers_cost` as the expected answer,
   in `contracts/conformance/realised/` ([DL-39](../../decisions/DL-39.md)). A rule we cannot
   reproduce is a failing test, not a guess.
3. `score_lineup`'s callers move to it; the season log's played row charges hits.

#### Acceptance criteria
- [ ] The scorer reproduces FPL's points for every entry in the corpus, including at least one
  auto-substitution, one vice-captain fallback and one double gameweek.
- [ ] The GW4 played row shows 79 (D-30).
- [ ] No other function in the repository computes a lineup's realised points.

### ORC-05: Evaluation step and season log from evaluations

#### Design
1. **Once per Finished gameweek**, for every strategy that has a record: xP accuracy from ORC-08's
   predictions; advice quality (the advised XI, captain and moves net of hits) against what the
   owner played and against the hindsight optimum; and today's reconciliation.
2. **The hindsight optimum is solved on real prices, clubs and bank** from silver as of the
   deadline (D-31); the `DP-WAIVER(DP-05)` in `publish/season_log.py` and its DL-93 waiver go.
3. **Stored once** as `ledger:evaluation/gwNN.json`, stamped with the scorer's version; recomputed
   only when that version changes.
4. **The season log, `models.json`'s live gameweeks and the live season's xP accuracy are built
   from evaluations**, not recomputed from the advice on every publish.

#### Acceptance criteria
- [ ] A Finished gameweek is evaluated once; a second run leaves `evaluation/gwNN.json` unchanged
  unless the scorer's version changed.
- [ ] The hindsight optimum respects the club limit and the owner's selling prices on a fixture
  where placeholder prices would choose differently.
- [ ] The season log and `models.json` match their current output for GW1–7 except where D-30 and
  D-31 change them, each change listed.

### ORC-06: Reproducible models history

- **Absorbs**: D-32.

#### Design
1. **The weekly backtest builds the models history** for every registered strategy over the archive
   seasons, scored by ORC-04, and appends it to `ledger`; the pipeline publishes it through the
   contract (WEB-04 moves the checked-in files).
2. **A strategy whose fit fails partway through the walk is recorded as not graded**; the others
   finish (D-32).
3. `scripts/models_history/` and `scripts/xp_accuracy/`, with their `/workspace` paths and the
   outside-repository simulator, are deleted; the frozen-era tables are archived as records (Q5).

#### Acceptance criteria
- [ ] A clean checkout rebuilds the models history with one command and no file outside the
  repository or the `ledger` and `data` branches.
- [ ] A strategy that raises at a later fold leaves the others graded and itself recorded with the
  reason.

## 5. Questions for the owner

Each has a recommended answer; "yes" accepts it.

1. **Advice of record.** When a strategy succeeds at T-3h and fails at T-45m, is the T-3h advice its
   record? *Recommended: yes, stamped with its `as_of`, the failure noted beside it.* The
   alternative, "no advice", throws away a valid recommendation because a later fetch failed.
2. **What is material.** Do any price change, any status or news change, any fixture move, and the
   first odds for the Open gameweek each start a pipeline run? *Recommended: yes, with runs
   queued newest-wins and the freeze applied.* Actions minutes are free on a public repository, so
   the limit is the deadline, not cost.
3. **Late-source cadence.** Is an hourly fast ingest within the deadline window enough? Today GitHub
   drops many of its firings, so the gaps run to four or five hours. *Recommended: add off-peak
   fallback firings, as `pipeline.yml` has, rather than a faster cron.*
4. **Chips in the scorer.** Does the one scorer cover Bench Boost, Triple Captain, Free Hit and
   Wildcard now? *Recommended: yes; the corpus will hold them as the league plays them.*
5. **Models history.** Rebuilt from today's registered strategies, its 2025/26 numbers will move
   from the frozen-era tables. Publish the rebuilt history and archive the old tables as records?
   *Recommended: yes.*
6. **The contract's minor version.** R1.3.0 adds fields to `week.json`, `models.json` and `meta`.
   Bring WEB-02's `contract_minor` and the app's runtime check forward into Drop A? *Recommended:
   yes; it is small, and it is what catches an old cached app reading new data.*
7. **Drops.** Two drops, A then B, each promoted when its boxes are ticked? *Recommended: yes.*
8. **Free Hit.** When do you expect to play your first Free Hit? D-33 must be repaid before then;
   if it is before Drop A lands, it becomes a hotfix.
9. **Run-time budgets.** A pipeline run within 5 minutes, the CI workflow within 3 and the Python
   tests within 90 seconds, with `pytest-xdist` added as a dev dependency? *Recommended: yes*: the
   T-45m run then finishes with most of the freeze to spare. **Answered yes, 2026-10-23.**
