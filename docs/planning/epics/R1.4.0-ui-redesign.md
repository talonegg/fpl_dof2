## 1. Overview

The app is regrouped around the questions a gameweek asks, in eight sections, and the pipeline
publishes the four things the new sections need that it does not yet: each model's options this
week, underlying expected points, each model's season as if it had played, and the rivals' moves,
plus the odds.

| # | Section | Holds |
| --- | --- | --- |
| 1 | **Home** | Your squad with last gameweek's points and next gameweek's xP; each model's recommended team and changes; key alerts and insights; a data-health summary; last gameweek's insights |
| 2 | **League** | The mini-league table; each team's last gameweek on a click |
| 3 | **Models** | Each model's description; this season's comparison, refreshed after each gameweek (the ladder of its advice on your squad, the ladder as if it had played, and predicted xP against underlying xP and actual points); the 2025/26 playthrough, static per model update |
| 4 | **Last gameweek** | Each model's advice against what you did, and against what happened; the hindsight optimum against each model's view of it; all gameweeks (the season log) |
| 5 | **This gameweek** | Each model's decision and the options it weighed; **Plan ahead**: the multi-week plan and the chip calendar |
| 6 | **Scouting** | Fixture difficulty; players, with everything every source holds on them; odds when posted |
| 7 | **Analysis** | The squad builder; compare players |
| 8 | **Data health** | Sources, stages, gates, runs and refresh details |

Settings sits behind a gear in the header. The model selector and the run banner (gameweek,
freshness, trigger, the trust caveat) are in one global header. The password gate, offline use and
the contract's refusal and warning screens are unchanged. Old paths redirect, so no link breaks.

**Where it starts** (survey of 2026-10-24): twelve routes (`/`, `/scout`, `/player/:id`,
`/compare`, `/squad`, `/fixtures`, `/league`, `/log`, `/models`, `/settings`, `/health`, and
`/history`, which already redirects into `/models`); five per-route loading hooks beside
`useArtefact`; one checked-in artefact, `web/public/static/xp_accuracy.json`; `web/src/data/`
importing `components/squad/effective`; `fpl-dof publish` rewriting `web/src/contract/types.ts` on
every run with no CI check; the bench ordered by xP in TypeScript and by P(plays) × xP in Python;
and two planning horizons (D-29).

## 2. Drop A — the new app on today's data

### WEB-03: Types checked in CI; publish writes nothing into `web/src`

- **Absorbs**: 03 §12 W4.

#### Design
1. `fpl-dof contract types` writes `web/src/contract/types.ts` from `contracts/`; `--check` fails
   when the file differs. The publish stage stops writing it.
2. The file stays checked in and CI's Python lint job runs the check, so the web build needs no
   Python (§5 Q1).
3. A `$defs` name collision fails generation instead of passing silently.

#### Acceptance criteria
- [ ] A schema change without regenerated types fails CI; a pipeline run leaves `web/src` untouched.
- [ ] Two schemas defining one `$defs` name with different shapes fail generation.

### WEB-04: Artefact registry and one loading hook

- **Absorbs**: 03 §12 W3, W5, W6; the rest of W2.

#### Design
1. **The artefact registry is generated** from the contract's `ARTEFACTS` into TypeScript beside the
   types: key, path, required or optional, warm offline or not. The offline warm-up list and the
   smoke check read it.
2. **One hook**: `useArtefact(key)` with `loading`, `ready`, `absent`, `malformed` and `error`;
   `useFixtures`, `useLeague`, `useLog`, `useHealth` and `useLazyArtefact` go, and with them the four
   spellings of "absent".
3. **Every artefact goes through `Contract.write`**: `web/public/static/xp_accuracy.json`, the
   2025/26 backtest's xP accuracy, is a frozen-era record nothing can rebuild, so it moves into the
   published data as a record, as the models history did with ORC-06.
4. **The data layer imports no component**: `effective.ts` moves into `web/src/data/`, and the
   effective squad is applied once.
5. **Bench order**: one rule in both languages, held in a lineup corpus both read (§5 Q2).

#### Acceptance criteria
- [ ] A new artefact needs one schema and one `ARTEFACTS` entry; the app, offline list and smoke
  check pick it up.
- [ ] A check fails if `web/src/data/` imports `web/src/components/`.
- [ ] Both languages pass the lineup corpus.

### D-29: One planning horizon

#### Design
`xp_horizon` reads `decision.horizon` (gameweeks and discount), as [DL-78](../../decisions/DL-78.md)
decided; `forecast.horizon_gameweeks` and `forecast.horizon_discount` go. This Week shows a horizon
xP the plan maximised.

#### Acceptance criteria
- [x] Changing `decision.horizon` moves `xp_horizon` and the plan together; no second horizon is
  configurable. Done: `tests/test_config.py::test_forecast_horizon_is_the_decision_horizon`.

### WEB-07: The eight-section shell

#### Design
1. **Navigation** is the eight sections of §1, declared once in `routes/nav.ts`, with each
   section's sub-views as tabs inside it. Narrow screens show the first sections in a bottom bar
   and the rest behind "More" (§5 Q3).
2. **The global header** carries the run banner, the model selector and the gear for Settings.
3. **Redirects** keep every old path: `/log` → Last gameweek, all gameweeks; `/squad` and
   `/compare` → Analysis; `/fixtures` → Scouting, fixtures; `/history` → Models, 2025/26.
4. **Data health** keeps its own section, last; Home shows its summary.

#### Acceptance criteria
- [ ] Every section and old path is reachable from the keyboard and at 375 px width, with no
  horizontal scroll.
- [ ] Every old path lands on its new view.
- [ ] `verify:browser` (layout, accessibility, offline) and the deployed smoke test pass.

### WEB-08: Home

#### Design
One screen answers "where am I and what should I do": your squad with each player's points last
gameweek and xP next; each model's recommended changes and captain, its expected points beside
roll, linked to This gameweek; the alerts that matter now (deadline, a waiting source, a gate,
a chip expiring); the data-health summary; and last gameweek's headline (your points, the best
model's, the hindsight optimum's, the biggest miss).

#### Acceptance criteria
- [ ] Every model's recommendation shows on Home from `models.json`, an unavailable model with its
  reason.
- [ ] With no published log, Home renders without last gameweek's card and says why.

### WEB-09: League

#### Design
The table as today; a row opens that team's last gameweek: XI, bench, captain and each player's
points, from `league.json` joined to the players' gameweek points. Drop B adds transfers, hits,
chip and differentials (ORC-14).

#### Acceptance criteria
- [ ] Clicking any published team shows its XI, captain and points; a team whose squad was not
  published (past `squad_limit`) says so.

### WEB-10: Models

#### Design
Each model's description and outline from `strategies.json`; this season: the ladder of each
model's advice on your squad (`models.json`) and the accuracy of predicted xP against actual
points (`xp_accuracy`); the 2025/26 playthrough (`models_history.json`). Drop B adds the
"as if played" ladder (ORC-13) and underlying xP (ORC-12).

#### Acceptance criteria
- [ ] The season ladder and the 2025/26 playthrough each rank every model, and say which is which.

### WEB-11: Last gameweek

#### Design
For the last evaluated gameweek: each model's advice against what you played and against what
happened (`models.json` actuals, `log.json` advised and played); the hindsight optimum with its
options and the oracle diagnostics, with each model's xP for the players that decided it. **All
gameweeks** is the season log, moved here. Drop B sets each model's forward options beside the
hindsight options (ORC-11).

#### Acceptance criteria
- [ ] Every model's points, your points and the optimum's net points show for the gameweek, and any
  earlier gameweek can be chosen.

### WEB-12: This gameweek and Plan ahead

#### Design
Each model's decision for the open gameweek: transfers, XI, captain, bench and expected points,
with "Why this number", the roll comparison and the bet you are making. **Plan ahead** holds the
multi-week plan and the chip calendar, with set 1's expiry. Drop B adds each model's options
(ORC-11).

#### Acceptance criteria
- [ ] Switching model changes the decision shown; roll is always shown beside it (FR-24).
- [ ] Plan ahead shows the chip calendar and the gameweeks left before set 1 expires.

### WEB-13: Scouting

#### Design
The fixture ticker and the scout table, and the player page with everything the sources hold on a
player (FPL and the archive; Understat and FBref are blocked upstream, D-23). Drop B adds odds
(ORC-15).

#### Acceptance criteria
- [ ] Fixtures and players are tabs of one section, and a player opens from either.

### WEB-14: Analysis

#### Design
The squad builder (locks, re-optimise, legality, the plan week by week) and compare players, as
today, under one section. A player selected in Scouting can be sent to compare.

#### Acceptance criteria
- [ ] Both tools work as before, at the new paths.

### EXP-01: Goalkeepers leading the horizon xP (D-34)

#### Design
Recheck the live `players.json` now that the training rows are current (R1.2.4). If goalkeepers no
longer lead, D-34 closes. If they do, a declared experiment on the saves and clean-sheet terms, its
falsifier written first, runs in the weekly backtest.

#### Acceptance criteria
- [ ] D-34 is closed with the recheck's numbers, or an experiment record with a verdict exists.

### EXP-02: Chip timing (D-21)

#### Design
A declared experiment replays chip timing (`optimise/replay.py`) at all three risk dials, with and
without the per-gameweek discount inside the percentile ranking, in the weekly backtest. It changes
no live behaviour; a fix clears the E8 §5 bar with its own DL entry.

#### Acceptance criteria
- [ ] A verdict on D-21's mechanism exists before the GW15 deadline.

## 3. Drop B — the data the new sections need

### ORC-11: Each model's options this gameweek

#### Design
Each model's decision publishes the option set the hindsight optimum uses (`log_hindsight_plan`):
roll, best single transfer and best overall, with moves, captain, points before hits, hits, net and
gain over roll, plus the chip scenarios the plan enumerates. One shape for both directions lets Last
gameweek set what each model weighed beside the optimum. The extra solves stay inside the pipeline
run's 300 s budget, or move to a job of their own after it; the budget is not raised.

#### Acceptance criteria
- [ ] This gameweek shows each model's roll, best single and best overall; Last gameweek sets them
  beside the hindsight options.
- [ ] The pipeline run stays within 300 s.

### ORC-12: Underlying expected points

#### Design
For each player and evaluated gameweek, the points the game's rules give to what he produced:
minutes and FPL's own expected goals, expected assists and expected goals conceded, read from
silver, scored under `rules` config (Invariant 2). The evaluation publishes predicted xP,
underlying xP and actual points, so a model's miss splits into forecast error (predicted against
underlying) and luck (underlying against actual).

#### Acceptance criteria
- [ ] No scoring value outside `rules` config; a test pins one gameweek's underlying xP for a
  player against a hand calculation from the config.
- [ ] Models shows, per model, forecast error and luck for each gameweek.

### ORC-13: The live season as if each model had played

#### Design
The ORC-06 replay runs over the live season: each model picks its own squad for GW1 under the
budget and plays every gameweek with its own transfers, chips and hits, fitted only on what was
knowable at each deadline (Invariant 5). Gameweeks before a model went live are labelled
**replayed**, later ones **live**. The weekly backtest job refreshes it once a gameweek is
Evaluated.

#### Acceptance criteria
- [ ] Models shows the "as if played" ladder with each gameweek labelled replayed or live.
- [ ] The job's run time is measured and within its workflow's budget.

### ORC-14: Rivals' moves and differentials

#### Design
The slow ingest fetches each published rival's gameweek history and transfers from FPL's public
entry endpoints once a gameweek is Finished, capped at `squad_limit` (no login, Invariant 4).
`league.json` gains each team's transfers, hit cost and chip. League's drill-down shows them, and
the differentials against your team with the points each swing was worth.

#### Acceptance criteria
- [ ] A rival's drill-down shows their transfers, hits, chip and differentials against you.
- [ ] A rival's fetch failing degrades that team's drill-down only (NFR-15).

### ORC-15: Odds published per fixture

#### Design
football-data.co.uk's match and over/under 2.5 odds, with the bookmaker margin removed, are
published in `fixtures.json` for upcoming fixtures. Scouting shows them beside the model's expected
goals and difficulty. Before they are posted: "Odds not posted yet; next check at …", as ORC-07
words it. There are no player odds; no free source has them.

#### Acceptance criteria
- [ ] A fixture with odds shows the probabilities beside the model's view; one without says when the
  next check is.

## 5. The owner's answers

Answered 2026-10-24; the recommended answer was accepted each time.

1. **Types in the build.** 05 §7.3 says the web build generates the types. Keep them checked in
   with a CI diff check instead, so the web build needs no Python? **Yes.**
2. **Bench order.** Which rule is right, P(plays) × xP (Python's, the auto-substitution value) or
   xP (what the app shows today)? **P(plays) × xP, in both**; the app adopts Python's rule.
3. **Narrow screens.** Eight sections do not fit a phone's bottom bar. Show Home, This gameweek,
   Last gameweek, League and Scouting, with Models, Analysis and Data health behind "More"?
   **Yes**; the model selector and the gear stay in the header.
