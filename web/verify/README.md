# Browser verification

`browser-check.mjs` drives real Chromium against a **built and served** site — not a dev server and
not jsdom — because the things it checks only exist in a browser: layout at a given width, whether
the page scrolls sideways, whether anything reaches the network, whether a service worker actually
serves the app with the network off, and how long any of it takes on a phone.

It must run against a **built** site specifically: the service worker is only generated by
`vite build` (`devOptions.enabled` is false, deliberately — a caching layer between the editor and
the browser is how an afternoon disappears), so phases 3 and 4 have nothing to check on a dev server.

## Running it

```bash
npm run build
npx vite preview --port 4173 --host 127.0.0.1 --strictPort   # in one terminal
npm run verify:browser -- http://127.0.0.1:4173              # in another
```

Screenshots land in `verify/screenshots/` — one per viewport at load, one after interacting, and
`offline.png`, which is the app rendering with the network switched off.

## The four phases

| Phase | What it covers |
| --- | --- |
| 1 · Layout and interaction | Three viewports; routing, filtering, sorting, theming, no horizontal scroll |
| 2 · Accessibility (NFR-14) | Keyboard reachability and operability, focus rings, colour-independent charts |
| 3 · Progressive web app (FR-34) | Manifest, service worker, and the app opening offline with real data |
| 4 · Performance (NFR-04, Q-06) | Emulated Pixel 5 on throttled 4G — FCP, payload, scout interaction latency |

Phase 4 prints its measurements whether or not they pass, because a budget met by a hair and a budget
met twentyfold call for different decisions and a bare PASS cannot tell them apart.

## What it checks, and why

| Check | Why it is here |
| --- | --- |
| Mobile 390×844, tablet 820×1180, desktop 1440×900 | The three widths E0-S7 must work at. Phone access over the LAN is the point of `vite --host` |
| No horizontal page scroll | The most common responsive failure, and invisible in a unit test |
| Nothing escapes the viewport **outside a scroller** | A wide table inside its own `overflow-x: auto` is the intended pattern; an element escaping with no scroller above it is a bug |
| Eleven starters, four substitutes | The squad is the deliverable. A pitch that renders ten players is wrong in a way that reads as fine |
| `±` appears with expected points | Invariant 6 — a mean is never shown without its uncertainty |
| Filter, search, sort, select | E0-S7 requires all of it client-side |
| Sorting **inverts** when toggled | Weaker checks pass by accident: the most expensive player is also the highest scoring, so changing the sort *column* leaves the top row unchanged. Toggling direction is the check that cannot pass by luck |
| Every route resolves to something | E6-S1 ships the shell before the views. A placeholder route that rendered nothing would be indistinguishable from a broken build, so each one is checked by the `data-testid` naming the story that fills it — including the unknown-route view |
| Navigating routes re-fetches nothing | The caching half of DL-35, and the only place it can be observed against a real network stack. Route changes must be renders, not requests |
| No page reload during interaction | `performance` navigation entries stay at 1 — which, now that navigation is client-side, also proves the router is not falling back to full page loads |
| The theme toggle changes real colours | Comparing the *computed* body background before and after. A check on the `data-theme` attribute alone would pass even if the token layer defined no light values, which is exactly the failure worth catching |
| The theme choice survives a reload | Persistence is the point of the toggle; this is the one place a deliberate reload belongs, and it runs after the no-reload check above |
| **No external network requests** | Invariant 8 / DL-03: the browser reads published static artefacts and calls no API. This is the only place that can actually be observed — and it is re-checked with the service worker active, since a caching layer is exactly where a stray origin could hide |

### Phase 2 — accessibility

| Check | Why it is here |
| --- | --- |
| Every control reached by pressing **Tab** | ARIA can be perfect on a control nothing can reach. The only way to know is to try |
| A **visible focus ring** on every keyboard-focused control | `:focus-visible` is checked, because that is the selector `index.css` hangs the ring on and the one a keyboard tab matches. This is the check that catches an `outline: none` added for looks |
| No positive `tabindex` | It reorders the whole page around one element, and is invisible until someone tabs |
| Controls **operated**, not just focused | Filters, sort headers, the theme toggle and the builder are driven with Enter. A header that sorts on click but not on Enter is the most common keyboard failure in a data table |
| The theme toggle checked by **attribute**, not colour | It cycles system → light → dark, so one press can land on a theme that looks identical to the one the system had already picked |
| Charts have an accessible name **and a written summary** | NFR-14. A chart that exists only as a picture is a chart half the readers do not get |
| Every fixture cell carries its difficulty as **text** | Colour may never be the only carrier. The grid prints each score, names each band, and explains the shading in an on-page legend, so it reads in greyscale |

### Phase 3 — progressive web app

| Check | Why it is here |
| --- | --- |
| Manifest name, short name, start URL, display, colours, icons | Chromium's installability criteria, checked one at a time so a failure says which one |
| Every icon the manifest names **exists** | A manifest naming a missing file looks installable and produces a blank launcher tile |
| `theme-color` metas match the tokens | `index.html` restates two token values because a `<meta>` cannot read a custom property. This keeps the restatement honest |
| The service worker **activates** | Registered is not running |
| The published artefacts are in the **runtime** cache | They are network-first and deliberately not precached (DL-38). This confirms the cache the worker reads was actually populated — it was not, on the first run, which is why `data/offline.ts` exists |
| **The app opens with the network off** | The whole story. It must render eleven starters, not merely load: a shell that opens to an empty page has cached the app and lost the point |
| Offline, the header still says **"As at …"** | DP-15: a cached publication must announce its own age rather than pass as current |

### Phase 4 — performance and Q-06

| Check | Why it is here |
| --- | --- |
| Emulated **Pixel 5** + CDP throttling at Lighthouse's mobile profile + 4× CPU | NFR-04 states its budget against *simulated* mobile 4G. A phone is not a desktop with a small screen, so the CPU is throttled too |
| **p95** FCP over ten cold loads, each in a fresh context with the worker blocked | The budget is stated as a p95, so it needs a distribution. One sample is an anecdote, and a warm cache would make the number a fiction |
| Initial payload split into **code and data** | So a miss says which half to fix |
| Scout **interaction latency**, measured in-page | Q-06's measurement. `Date.now()` across the driver would include Playwright's own round trip, which on a throttled context is the same order as the thing being measured |
| Each measured step forced to **genuinely change state** | Otherwise the wait times out and the timeout gets recorded as the latency — which is how a 10-second reading appeared on the first run |
| A step the table never responded to records **`NaN`** | It propagates through `Math.max` and fails the budget, so an unresponsive table cannot quietly score well |
